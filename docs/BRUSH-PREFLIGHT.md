## Input and camera contract

Brush discovers the largest COLMAP model by `cameras.bin` / `images.bin` and reads `points3D.bin` in that same directory. The tested input has `dense/sparse/{cameras.bin,images.bin,points3D.bin}` and `dense/images/<registered-name>`; all 60 names resolve, with no `dense/masks` directory. It uses the undistorted PINHOLE camera, so no distortion translation is needed. In the audited source, COLMAP poses are interpreted as world-to-camera and inverted to Brush camera-to-world; principal point is normalized by image width/height. [The v0.3 loader](https://github.com/ArthurBrussee/brush/blob/3edecbb2fe79d3e2c87eeab85b15e0b1dd10d486/crates/brush-dataset/src/formats/colmap.rs) has the same inversion and normalization. Pixel-center/renderer equivalence and visual pose orientation remain untested without a real render.

The audited newer source looks for optional `masks/` and its default `eval_split_every=None` puts every loaded view in training. The proposed v0.3 command omits `--eval-split-every` and does not supply masks. This avoids an *implicit* in-dataset holdout, but does not establish that no external held-out/reference files were added elsewhere. The preflight optionally verifies a `brush_train_split_v1` JSON manifest with `train_image_sha256` (exact name→SHA map for **every** registered image) and a disjoint `heldout_image_sha256` map. Even with that manifest, `training_authorized` stays false until the producer/dataset lineage and external-input boundary are reviewed. Do not use the YCB Google/reference mesh, sensor-depth or fitted registration to create or tune Brush training inputs.

The bounded launcher (`python3 -m scripts.brush_backend.smoke`) requires the exact fresh external output path on a separately mounted volume and the exact verified release binary. ## v0.3.0 masked-input bridge

The **release commit's** [COLMAP loader](https://github.com/ArthurBrussee/brush/blob/3edecbb2fe79d3e2c87eeab85b15e0b1dd10d486/crates/brush-dataset/src/formats/colmap.rs), [mask lookup](https://github.com/ArthurBrussee/brush/blob/3edecbb2fe79d3e2c87eeab85b15e0b1dd10d486/crates/brush-dataset/src/formats/mod.rs), and [exact-stem VFS lookup](https://github.com/ArthurBrussee/brush/blob/3edecbb2fe79d3e2c87eeab85b15e0b1dd10d486/crates/brush-vfs/src/lib.rs) require a sibling `masks/` directory with a mask whose **file stem equals the image file stem**. For `images/NP3_000.jpg`, the existing OpenMVS name `NP3_000.mask.png` does **not** match. The bridge copies its bytes to `masks/NP3_000.png`. This release's [image loader](https://github.com/ArthurBrussee/brush/blob/3edecbb2fe79d3e2c87eeab85b15e0b1dd10d486/crates/brush-dataset/src/scene.rs) copies the grayscale mask's first channel into alpha **before** resizing. The [training loss](https://github.com/ArthurBrussee/brush/blob/3edecbb2fe79d3e2c87eeab85b15e0b1dd10d486/crates/brush-train/src/train.rs) multiplies RGB error by alpha when it is a separate mask: 255 keeps, 0 ignores. This is loss masking, not transparent-background compositing; it does not remove sparse initializer points in the background. The release loader zips pixels without an explicit mask-dimension guard, so our adapter rejects any mode or dimensions other than 8-bit grayscale PNG exactly matching the registered 1282×1024 RGB JPEG, with binary 0/255 alpha.

`python3 -m scripts.brush_backend.mask_bridge` is read-only and verifies the sealed 008 mask report, all 60 undistorted image/model hashes, all 60 PNG mask hashes/pixel classes, filename uniqueness, and external free-space reserve. After peer review, the bounded `--prepare` completed in 6.59 seconds. The prepared dataset is `/Volumes/backups/code/crispmesh-data/brush-ycb-masked-input-001/dataset`, with byte-identical `images/` and `sparse/` plus the renamed-mask `masks/`; its [bridge report](/Volumes/backups/code/crispmesh-data/brush-ycb-masked-input-001/bridge-report.json) (SHA-256 `7ef45e2ff8e5997d2079f5af508ef2f4623347cd3ac8335d7e3abc75e260e62d`) sits **outside** the dataset folder. It sealed 123 files: 60 RGB JPEGs, three model binaries, and 60 grayscale PNGs, totalling 54,754,350 copied bytes. It copies no reference mesh, sensor depth, labels, or held-out views. The operation had a 256 MiB output cap, 240-second deadline, and 10 GiB external reserve. These coarse photo-derived masks are pose-support regions, **not exact object silhouettes**; substantive masked Brush training and appearance/geometry quality remain untested.

The separately approved 20-step masked **execution smoke** used the same v0.3 binary, `--max-resolution 640`, `--max-splats 50000`, seed 42, and export at step 20 as the unmasked smoke. [`brush-masked-smoke-001/report.json`](/Volumes/backups/code/crispmesh-data/brush-masked-smoke-001/report.json) SHA-256 `d290b483a8916678d032077de6717d980556320dbc3b9970f954cd566cb08403` records stage exit 0 in 7.099 seconds (wrapper 8.814 seconds), sampled process RSS peak 343,851,008 bytes, and unchanged hashes for all 123 prepared files and the binary. The finite Gaussian PLY has 3,939 vertices (the sparse initializer count), SHA-256 `d68c88057cc098eecc841c65ea66591ea3a158eed08ba7dd4f68f2f8422aaa34`. The unmasked and masked export hashes differ, but this alone does not prove which pixels influenced training; `train.log` was empty and the release did not report mask attachment. This smoke is **not** an object-quality, held-out rendering, or mesh comparison. No long masked training was run. The actual masked-001 runner continuously enforced the **external** 10 GiB floor; root observed ample internal space before/after, but internal space was not monitored during the run. A subsequent code change adds optional continuous internal-floor monitoring for future runs only; it must not be retroactively credited to masked-001.
